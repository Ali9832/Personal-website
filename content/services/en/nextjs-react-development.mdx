## Server Components changed the problem

The old React model was: the server sends an empty HTML shell, the browser downloads a few hundred kilobytes of JavaScript, then fetches data, then builds the page. Each step is a delay.

With the App Router and Server Components, a component that only renders data never reaches the browser at all. The JavaScript that ships is only the genuinely interactive parts.

```tsx
// Runs on the server; not a byte of this file reaches the browser.
export default async function InvoiceList({ customerId }: { customerId: string }) {
  const invoices = await db.invoice.findMany({
    where: { customerId },
    orderBy: { issuedAt: "desc" },
  });

  return (
    <ul>
      {invoices.map((invoice) => (
        <li key={invoice.id}>{invoice.number}</li>
      ))}
    </ul>
  );
}
```

The practical result is a page running on a few kilobytes of JavaScript instead of a few hundred.

## Deploying to ordinary hosting

This is the part that usually gets skipped and later gets expensive. Many Next.js projects drift into depending on platform-specific features and then will not run on a normal server.

What I do from the start:

- `output: "standalone"`, so the build output is a self-contained Node server.
- No `runtime = "edge"` anywhere.
- Image optimisation at build time rather than by the platform.
- Environment variables from a file, not from one vendor's dashboard.

<Callout title="What this means in practice">
The build output starts with `node server.js`. It runs behind PM2, Passenger, or whatever your host provides.
</Callout>

## When Next.js is the wrong call

If your site is five content pages that change twice a year, Next.js adds complexity for nothing. The same applies if your team only knows PHP and will maintain it themselves. I say this before the project starts, not after the invoice.
